# Phase 2 전처리 비교 (MPSC · steel-ocr)

OpenCV 기본 보정(작은 사진 키우기 · 노이즈 제거 · CLAHE 대비 보정)을 켰을 때와 껐을 때 문자 인식 정확도를 비교했습니다. 결론은 **대비 보정은 기본값에서 끄고, 작은 사진 키우기 + 노이즈 제거는 유지**입니다.

- 측정일: 2026-10-09
- 환경: Claude Managed Agents 원격 컨테이너 (CPU 4개, Linux, Python 3.12, PaddleOCR 3.7.0) — `vision/tools/remote_eval.py`
- OCR 설정: `vision/src/vision/ocr.py`의 `DEFAULT_CONFIG` (Phase 1과 같음)
- 전처리 설정: `eval_ocr.py --prep` (`none`, `up`, `clahe`, `up+clahe`, `default`)
- `default`는 측정 당시 기본값(노이즈 제거 + 키우기 + 대비 보정)

## 알게 된 것

1. **대비 보정은 금속 사진에서 오히려 나빠짐.**
   - steel-ocr 표기를 하나씩 짝지어 보면 나빠진 표기 17개, 좋아진 표기 7개, 같은 표기 27개
   - 금속 표면의 결과 녹이 글자와 함께 강조돼 `b`→`6`, `S`→`5` 같은 오류가 늘고 글자 일부가 잘림 (예: `B1Sb30N-7A` → `15-7A`)
   - MPSC에서는 300장 기준 차이가 0.002로 효과가 없음
   - 켜 두면 보정 강도(`correction_strength`)만 올라가 3단계 신뢰도가 이유 없이 깎이므로 **기본값에서 끔**
2. **키우기는 MPSC에서 효과가 없고 시간만 42% 늘어남.**
   - 긴 변 1280px 미만 사진(300장 중 표기 805개)만 보면 CER 0.553 → 0.557, 표기 찾음 46.8% → 47.6%
   - MPSC의 작은 사진은 대부분 글자 영역을 잘라낸 사진이라 글자가 이미 큼
   - 운영측 예시 사진(343px)은 키우기 전에는 글자를 거의 못 찾고 키운 뒤 2~5개 찾았으므로 **유지**. 1280px 이상인 일반 휴대폰 사진에는 적용되지 않아 속도 영향이 없음
   - 운영측 사진 정답이 생기면 그 사진으로 다시 판단
3. **키울 때 노이즈 제거를 함께 하는 쪽이 나아 보임.** 50장의 작은 사진에서 `키우기 + 대비 보정` CER 0.572, 노이즈 제거를 더하면 0.544. 표기 수가 적어 확정은 아니므로 기본값 유지만 결정
4. **50장 평가는 우연 오차가 큼.**
   - 같은 설정도 앞 50장만 보면 CER이 0.02씩 달라짐. 300장에서 보이는 설정 간 차이보다 10배 큼
   - 50장은 큰 차이를 빠르게 거르는 용도로만 쓰고, 미세한 차이는 300장 이상으로 확인

## 노이즈 제거 끔 (추가 결정)

MPSC 비교에서는 노이즈 제거를 유지했지만, 운영측 손글씨 예시를 보니 **흰 철판 위의 흐린 흰 글씨를 배경으로 뭉개 버림**:

| 운영측 손글씨 | 획 대비 (밝은 획 상위 2% − 배경 중앙값): 노이즈 제거 + 키우기 → 키우기만 |
| --- | --- |
| 예시 1 (회색 철판) | 54 → 55 |
| **예시 2 (흰 철판, 흐린 흰 글씨)** | **8 → 21** — 노이즈 제거 후에는 사람도 거의 못 읽음 |
| 예시 3 (어두운 철판) | 85 → 86 |

과제의 핵심인 손글씨를 지우는 보정이라 기본값에서 끔. 2단계도 Claude에는 원본을 노이즈 제거 없이 키워서 보냄.

## 남은 보정 검토 (원근 · 조도 · 반사 · 곡면)

조건부 보정을 만들기 전에, 우리 데이터에서 각 조건이 실제로 오류를 늘리는지 먼저 확인했습니다. 전처리 없이 돌린 결과(steel-ocr 110장, MPSC 300장)를 표기마다 정답 영역의 촬영 조건과 묶었습니다.

| 조건 (정답 영역 기준) | steel-ocr CER | MPSC CER | 판단 |
| --- | --- | --- | --- |
| 어두움: 평균 밝기 100 미만 / 이상 | 0.41 (8개) / 0.37 | 0.56 (355개) / 0.54 | 차이 없음 → 조도 보정(Retinexformer) 보류 |
| 반사: 밝기 245 이상 픽셀 5% 이상 / 미만 | 0.74 (9개) / 0.35 | 0.51 (88개) / 0.55 | steel-ocr 9개뿐, MPSC는 오히려 낮음 → 반사 제거(SIHR) 보류 |
| 원근: 정답 사각형 모서리가 직각에서 15° 이상 / 미만 | **0.70 (46개) / 0.25** | 0.49 (91개) / 0.55 | steel-ocr에서만 큼 |
| 휨 | 해당 표기 없음 | 해당 표기 없음 | 곡면 펴기(UVDoc) 보류 |

- 운영측 블록 사진(`block/3`)의 밝은 영역 31%는 반사가 아니라 흰 벽 배경

### 원근 보정

정답 사각형으로 표기 영역을 잘라 PaddleOCR로 읽은 상한 실험 (steel-ocr, 원근 큰 표기 46개 · 작은 표기 46개):

| 자르는 방법 | 원근 큰 표기 CER | 원근 작은 표기 CER |
| --- | --- | --- |
| 그냥 자르기 | 0.513 | 0.115 |
| 회전만 바로잡기 | 0.509 | 0.120 |
| 사다리꼴을 직사각형으로 펴기 | **0.316** | 0.109 |

사다리꼴을 알면 효과가 크지만, 사진에서 자동으로 찾는 방법은 둘 다 실패했습니다 (원근 큰 사진 12장, 표기 33개):

- 검출 윤곽(DB 다각형)의 위·아래 변에 직선 맞추기: CER 0.547 → 0.529. 큰 글씨는 검출 영역이 폭이 일정한 덩어리라 사다리꼴이 거의 직사각형으로 나옴
- 글자 획의 위·아래 끝선에 직선 맞추기: 변화 없음

### 확대 재판독 (`OcrConfig.zoom_reread`, 기본 꺼짐)

원근 대신 해상도 문제를 풀어 보았습니다. 찾은 글자 영역을 원본 해상도로 넉넉히 잘라 한 번 더 검출+인식하고, 평균 확률이 높으면 글자만 바꿉니다 (위치는 원래 검출 그대로). `eval_ocr.py --zoom`

| 데이터 (50장) | CER | 표기별 좋아짐 / 나빠짐 | 사진당 시간 |
| --- | --- | --- | --- |
| steel-ocr (4032px) | 0.297 → **0.232** | 12 / 2 | 맥북 12장 기준 +50% |
| MPSC (대부분 1280px 이하) | 0.489 → 0.505 | 4 / 8 | 1.22 → 2.11초 (원격) |

- 큰 사진은 검출할 때 1280px로 줄면서 작은 글씨가 뭉개지는데, 다시 잘라 읽으면 이게 풀림
- 이미 글자 영역만 잘라 둔 작은 사진(MPSC)은 얻는 게 없고 조각이 달라져 조금 나빠짐 → **기본값은 끔**. 검출 때 많이 줄어드는 큰 사진에만 켜는 조건부 적용은 다음에 측정

### 운영측 손글씨 (참고)

운영측 손글씨 예시 3장(글자 줄 7개, 위치는 사람이 지정)은 PaddleOCR, TrOCR(`microsoft/trocr-base-handwritten`), TrOCR + 형식 제한 디코딩(`[FVS]` + 숫자만 출력) 모두 0/7. TrOCR은 영어 단어(`gleeves`, `often`)로 읽고, 형식을 제한해도 확률이 거의 0 → 손글씨 F·V·S 데이터 수집과 추가 학습이 필요 (Phase 4)
